用 Astro 7 搭建个人博客的架构决策

发表于2026-10-03|更新于2026-10-04
|浏览量:

选博客技术栈时，第一个要分清的不是框架，而是你的站点属于内容型还是应用型。

两种站点的本质差异

内容型站点的核心动作是「读」，用户点进来看文字，然后离开。应用型站点的核心动作是「交互」——登录、填表、实时更新、状态流转。

这个差异决定了架构：

维度 内容型 应用型
首屏 JS 预算 0–12 KB 80 KB 起
是否需要服务端 不需要 需要
断网后能否阅读 能（Service Worker） 视情况
攻击面 几乎为零 数据库 + 认证 + API

为什么博客不需要后端

文章是发布时确定、发布后不变的内容。既然不变，就没有理由在每次访问时重新计算。

把它编译成静态 HTML 之后：

  • 服务器只是一堆文件，没有可执行逻辑
  • 没有数据库，就没有 SQL 注入
  • 没有登录页，就没有暴力破解
  • 成本从「服务器月租」变成「CDN 免费额度」

这也是我不建议用 WordPress 的原因。WordPress 承载了全网 43% 的站点，但 2025 年 Patchstack 报告的 13000+ 插件漏洞里，90% 以上来自插件——它把 PHP 执行、MySQL、可写文件系统全部暴露在公网上。

岛屿架构解决了什么

Next.js 这类框架的问题不是「慢」，而是它假设你的页面总是应用的。React runtime、路由、hydration 逻辑会无条件发到浏览器，即使页面只有一段文字。

有实测数据：同类博客页面，Astro 首次加载 0–9 KB JS，Next.js 是 80–463 KB。Lighthouse 上前者 100 分，后者 88 分。

岛屿架构的思路是反过来：HTML 是默认状态，JS 是例外。只有需要交互的组件才标记为 island，其余部分保持纯静态。

client:visible 意味着用户滚动到视口内才加载脚本，首屏完全不付这个成本。

一个真实的性能对比

我在自己的站上做过一次迁移，从 Next.js App Router 换到 Astro：

  • 首屏 JS：112 KB → 0 KB（博客页）
  • Lighthouse Performance：88 → 100
  • 构建时间：45 s → 2 s

构建时间的差异在高频发布时才会显现出来——每次改一个错别字都要等 45 秒，一天几十次就是几十分钟的纯等待。

国内托管的现实约束

这是很多技术文章不提但绕不开的部分。按国内访问延迟排序：

  1. EdgeOne Pages（腾讯云，备案后）：50–90 ms
  2. Cloudflare Pages：联通晚高峰 800 ms+
  3. Vercel：部分地区不可达
  4. GitHub Pages：极慢

如果不做备案，可用选项是 Cloudflare Pages 或 EdgeOne 国际站，代价是晚高峰延迟。实测有开发者从 Cloudflare 迁到 EdgeOne 后，联通线路从 800 ms 降到 200 ms——但这依赖备案启用国内节点，不备案拿不到这个收益。

总结

内容型站点选 Astro，应用型站点选 Next.js。这不是哪个框架更好的问题，是匹配工作负载的问题。试图什么都做的框架，通常两件事都做不好。
